# Техническое задание (полная спецификация)

## Автоматизированная информационная система интернет-магазина компьютерной техники и периферии «PeriphShop»

**Версия документа:** 1.0
**Дата:** 2026-09-08
**Статус:** утверждено к реализации

---

## 1. Общие сведения

### 1.1. Наименование системы

Полное наименование: *Автоматизированная информационная система интернет-магазина компьютерной техники и периферии*.
Условное (рабочее) наименование: **PeriphShop**.

### 1.2. Назначение системы

Система предназначена для автоматизации полного цикла розничной торговли компьютерной
периферией и комплектующими через сеть Интернет: от ведения каталога товаров и складских
остатков до оформления, оплаты, сборки и выдачи заказа, а также для оперативного контроля
показателей работы магазина средствами мониторинга.

### 1.3. Цели создания

| № | Цель | Показатель достижения |
|---|------|----------------------|
| Ц-1 | Снизить трудозатраты на приём и обработку заказа | Ручные операции менеджера ≤ 3 на заказ |
| Ц-2 | Исключить продажу товара, отсутствующего на складе | Списание остатка в транзакции оформления заказа |
| Ц-3 | Обеспечить покупателю самостоятельный подбор товара | Фасетный фильтр по ≥ 6 параметрам, поиск по названию/SKU |
| Ц-4 | Обеспечить наблюдаемость системы | Метрики, логи и дашборды доступны в Grafana |
| Ц-5 | Обеспечить воспроизводимое развёртывание | Полный стенд поднимается одной командой `docker compose up` |

### 1.4. Границы системы

**Входит в систему:** каталог товаров, поиск и фильтрация, корзина, оформление заказа,
личный кабинет покупателя, рабочее место менеджера и администратора, учёт складских остатков,
промокоды, отзывы и рейтинги, аутентификация/авторизация, аудит действий, мониторинг и логирование.

**Не входит (вне границ):** реальная интеграция с банковским эквайрингом (реализуется имитатор платежа),
интеграция с 1С/бухгалтерией, курьерская логистика в реальном времени, мобильное приложение,
рекомендательная система на машинном обучении.

### 1.5. Термины и сокращения

| Термин | Определение |
|--------|-------------|
| АИС | Автоматизированная информационная система |
| SKU | Stock Keeping Unit, уникальный складской артикул товара |
| Товар | Единица номенклатуры, доступная к продаже |
| Позиция заказа | Товар + количество + зафиксированная цена в составе заказа |
| Корзина | Временный набор позиций до оформления заказа |
| Фасет | Параметр фильтрации каталога (бренд, цена, категория, характеристика) |
| JWT | JSON Web Token, формат токена доступа |
| RBAC | Role-Based Access Control, ролевая модель разграничения доступа |
| API | Программный интерфейс приложения (в системе — REST/JSON) |

## 3. Функциональные требования

Требования пронумерованы как **FR-xx**; каждое проверяемо и отражено в API и UI.

### 3.1. Каталог и номенклатура

- **FR-01.** Система обеспечивает иерархический каталог категорий (до 3 уровней вложенности), например «Периферия → Клавиатуры → Механические».
- **FR-02.** Система хранит карточку товара: SKU, наименование, ЧПУ-адрес (slug), категория, бренд, описание, цена, старая цена (для скидки), остаток, признак активности, гарантия (мес.), вес, набор изображений, набор характеристик «имя–значение–единица–группа».
- **FR-03.** Система обеспечивает постраничный вывод каталога (по умолчанию 12 товаров на странице, максимум 100).
- **FR-04.** Система обеспечивает фильтрацию каталога по: категории (с учётом подкатегорий), бренду (множественный выбор), диапазону цены, наличию на складе, наличию скидки, минимальному рейтингу, поисковой строке (наименование, SKU, описание).
- **FR-05.** Система обеспечивает сортировку: по новизне, цене ↑/↓, рейтингу, популярности (числу продаж).
- **FR-06.** Система возвращает фасеты (доступные бренды с количеством товаров, границы цены) для текущего набора фильтров.
- **FR-07.** Карточка товара содержит блок «Похожие товары» — до 8 товаров той же категории.
- **FR-08.** Система ведёт счётчик просмотров карточки товара.

### 3.2. Пользователи и аутентификация

- **FR-10.** Регистрация покупателя по e-mail и паролю; e-mail уникален; пароль хранится только в виде хэша BCrypt (cost = 11).
- **FR-11.** Требования к паролю: длина ≥ 8 символов, наличие буквы и цифры.
- **FR-12.** Аутентификация выдаёт пару токенов: access-token (JWT, TTL 30 мин) и refresh-token (случайные 64 байта, TTL 14 дней, хранится в БД).
- **FR-13.** Обновление пары токенов по refresh-token с ротацией: использованный refresh-token отзывается.
- **FR-14.** Выход из системы отзывает refresh-token.
- **FR-15.** Профиль: просмотр и изменение ФИО, телефона, адреса доставки по умолчанию; смена пароля с подтверждением старого.
- **FR-16.** Администратор может блокировать/разблокировать пользователя и менять его роль; заблокированный пользователь не проходит аутентификацию.

### 3.3. Корзина

- **FR-20.** Гость имеет анонимную корзину, идентифицируемую GUID-идентификатором, который хранится на клиенте и передаётся в заголовке `X-Cart-Id`.
- **FR-21.** При входе пользователя анонимная корзина сливается с корзиной пользователя: количества по совпадающим товарам суммируются, но не превышают остаток.
- **FR-22.** Операции корзины: добавить товар, изменить количество, удалить позицию, очистить корзину, получить содержимое.
- **FR-23.** Корзина при выдаче пересчитывает актуальные цены и помечает позиции, у которых остаток стал меньше запрошенного количества.
- **FR-24.** Количество товара в позиции — целое от 1 до 99 и не более текущего остатка.

### 3.4. Оформление и жизненный цикл заказа

- **FR-30.** Оформление заказа доступно только аутентифицированному пользователю; корзина должна быть непустой.
- **FR-31.** При оформлении указываются: способ доставки (самовывоз / курьер / постамат), адрес (для курьера и постамата), ФИО и телефон получателя, способ оплаты (при получении / картой онлайн), комментарий, промокод (опционально).
- **FR-32.** Стоимость доставки: самовывоз — 0 ₽; курьер — 350 ₽, бесплатно при сумме позиций ≥ 5000 ₽; постамат — 200 ₽.
- **FR-33.** Итог заказа = сумма позиций − скидка по промокоду + стоимость доставки. Суммы округляются до 2 знаков.
- **FR-34.** В момент создания заказа выполняется транзакция: проверка остатков → списание остатков → фиксация цен в позициях → создание заказа → очистка корзины. При недостатке остатка транзакция откатывается с ответом `409 Conflict` и перечнем дефицитных позиций.
- **FR-35.** Номер заказа формируется по маске `ORD-ГГГГММДД-NNNN`, где NNNN — суточный счётчик.
- **FR-36.** Статусы заказа и допустимые переходы:

```
New ──► Paid ──► Processing ──► Shipped ──► Delivered ──► Completed
 │        │           │             │
 └────────┴───────────┴─────────────┴──────► Cancelled  (возврат остатков на склад)
                                    Delivered ──► Refunded
```

- **FR-37.** Покупатель может отменить свой заказ в статусах `New` и `Paid`. Менеджер может отменить заказ в любом статусе до `Delivered`.
- **FR-38.** При отмене или возврате заказа остатки товаров возвращаются на склад одной транзакцией.
- **FR-39.** Каждая смена статуса фиксируется в истории заказа (кто, когда, из какого статуса в какой, комментарий).
- **FR-40.** Оплата картой имитируется платёжным шлюзом-заглушкой: заказ переходит `New → Paid` по подтверждению; при оплате при получении переход в `Paid` выполняет менеджер.
- **FR-41.** При создании заказа и при смене статуса покупателю отправляется e-mail-уведомление (SMTP; в стенде — Mailpit).

### 3.5. Склад

- **FR-45.** Каждое движение остатка фиксируется записью: товар, дельта (+/−), причина (`Purchase`, `Sale`, `Cancellation`, `Correction`, `WriteOff`), ссылка на заказ, автор, время.
- **FR-46.** Остаток товара не может стать отрицательным; попытка приводит к ошибке.
- **FR-47.** Менеджер может выполнить приход/корректировку остатка с обязательным комментарием.
- **FR-48.** Система выделяет товары с остатком ниже порога (по умолчанию 5) в отчёте «Заканчивается на складе».

### 3.6. Отзывы и рейтинги

- **FR-50.** Оставить отзыв (оценка 1–5, заголовок, текст) может пользователь, у которого есть завершённый заказ с этим товаром; не более одного отзыва на товар от пользователя.
- **FR-51.** Отзыв публикуется после модерации менеджером.
- **FR-52.** Средний рейтинг и число отзывов денормализованы в карточке товара и пересчитываются при изменении набора опубликованных отзывов.

### 3.7. Промокоды

- **FR-55.** Промокод задаёт скидку в процентах либо фиксированной суммой, минимальную сумму заказа, период действия, лимит использований.
- **FR-56.** Проверка промокода доступна отдельным вызовом до оформления заказа.
- **FR-57.** Скидка не может превышать сумму позиций заказа; счётчик использований инкрементируется в транзакции создания заказа.

### 3.8. Отчётность (рабочее место менеджера)

- **FR-60.** Сводка: выручка и число заказов за период, средний чек, число новых покупателей.
- **FR-61.** Топ-10 продаваемых товаров за период.
- **FR-62.** Распределение заказов по статусам.
- **FR-63.** Отчёт «Заканчивается на складе».
- **FR-64.** Выгрузка списка заказов за период в CSV.

### 3.9. Аудит

- **FR-70.** Изменения справочников, ролей, остатков и статусов заказов записываются в журнал аудита: пользователь, действие, сущность, идентификатор, полезная нагрузка (JSON), IP, время.
- **FR-71.** Журнал аудита доступен только администратору, с фильтром по пользователю, сущности и периоду.

## 5. Архитектура системы

### 5.1. Общая схема

```
                         ┌────────────────────────────┐
                         │          Браузер           │
                         └──────────────┬─────────────┘
                                        │ HTTP(S)
                         ┌──────────────▼──────────────┐
                         │ Nginx (SPA + reverse proxy) │
                         └───────┬───────────┬─────────┘
                    статика SPA  │           │ /api →
                         ┌───────▼─────┐ ┌───▼──────────────────┐
                         │ Angular SPA │ │ ASP.NET Core Web API │
                         └─────────────┘ └───┬───────┬──────┬───┘
                                             │       │      │
                             ┌───────────────▼─┐ ┌───▼───┐ ┌▼────────┐
                             │     MySQL 8      │ │ Redis │ │ MinIO   │
                             │ (данные системы) │ │ кэш   │ │картинки │
                             └───────┬──────────┘ └───────┘ └─────────┘
                                     │ mysqld-exporter
        ┌─────────────┐  scrape   ┌──▼─────────┐  query   ┌──────────┐
        │  cAdvisor   ├──────────►│ Prometheus │◄─────────┤ Grafana  │
        │node-exporter│           └────────────┘          └────┬─────┘
        └─────────────┘                                        │ query
                     docker logs ──► Promtail ──► Loki ─────────┘
```

### 5.2. Слои backend

| Слой | Проект | Содержимое | Зависимости |
|------|--------|-----------|-------------|
| Домен | `PeriphShop.Domain` | Сущности, перечисления, доменные правила и исключения | нет |
| Приложение | `PeriphShop.Application` | DTO, интерфейсы, бизнес-сервисы, валидаторы, постраничность | Domain |
| Инфраструктура | `PeriphShop.Infrastructure` | EF Core `AppDbContext`, конфигурации сущностей, миграции, сид, JWT, хэш паролей, e-mail, кэш | Domain, Application |
| Представление | `PeriphShop.Api` | Контроллеры REST, middleware, аутентификация, Swagger, метрики, health-checks, DI | все выше |
| Тесты | `PeriphShop.Tests` | Юнит-тесты бизнес-логики (xUnit + EF InMemory) | все выше |

Правило зависимостей: направление только «наружу → внутрь», домен ни от чего не зависит.

```
   │             │◄──────────────────┤ 201 Created + номер заказа │
   │◄────────────┤ «Спасибо за заказ»│                            │
                 │                   ├─► метрика orders_created_total++
                 │                   ├─► письмо через SMTP (Mailpit)
```

**Обновление токена:**

```
SPA → API: POST /api/auth/refresh { refreshToken }
API: валидация токена в БД (не истёк, не отозван) → отзыв старого → выдача новой пары → 200 OK
При 401 SPA-интерсептор один раз пытается refresh, иначе — переход на /login
```

| Группа | Префикс | Доступ |
|--------|---------|--------|

| Каталог | `/api/catalog` | публично |
| Отзывы | `/api/reviews` | чтение публично, запись — Customer |
| Корзина | `/api/cart` | публично (по анонимному идентификатору) |
| Заказы | `/api/orders` | Customer |
| Промокоды | `/api/promo` | Customer |
| Избранное | `/api/favorites` | Customer |

### 7.1. Коды ответов

| Код | Смысл в системе |
|-----|-----------------|
| 200 / 201 / 204 | Успех |
| 400 | Ошибка валидации (перечень полей в `errors`) |
| 401 | Отсутствует или просрочен токен |
| 403 | Недостаточно прав по матрице RBAC |
| 404 | Сущность не найдена |
| 409 | Конфликт: недостаточно остатка, дубликат e-mail/SKU, недопустимый переход статуса |
| 422 | Нарушено бизнес-правило (например, промокод неприменим) |
| 429 | Превышено ограничение частоты запросов |
| 500 | Внутренняя ошибка (детали — в логах по `traceId`) |

## 9. Безопасность

1. **Аутентификация** — JWT HS256, секрет ≥ 32 байт из переменной окружения `Jwt__Key`; access 30 мин, refresh 14 дней с ротацией и отзывом.
2. **Авторизация** — атрибуты `[Authorize(Roles = ...)]` плюс проверка владения ресурсом (пользователь видит только свои заказы).
3. **Хранение паролей** — BCrypt, cost 11, индивидуальная соль.
4. **Транспорт** — HTTPS на периметре (Nginx), HSTS в продуктивном контуре.
5. **Валидация входных данных** — FluentValidation на всех командных DTO.
6. **Ограничение частоты** — `RateLimiter` ASP.NET Core: фиксированное окно 1 мин, 100 запросов на IP; отдельная политика 10/мин на `/api/auth/login`.
7. **Заголовки безопасности** — `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Content-Security-Policy`.
8. **Секреты** — только через переменные окружения / `.env`; файл `.env` в `.gitignore`.
9. **Аудит** — журнал критичных действий (FR-70), доступный только на чтение.
10. **Загрузка файлов** — только изображения (`image/jpeg`, `image/png`, `image/webp`), размер ≤ 5 МБ, имя генерируется системой.

### 10.1. Метрики приложения

| `periphshop_products_total` | gauge | Число активных товаров |

### 10.2. Дашборды Grafana (провижининг из репозитория)

1. **API Overview** — RPS, доля ошибок 4xx/5xx, латентность p50/p95/p99, топ маршрутов.
2. **Business** — заказы и выручка по времени, средний чек, добавления в корзину, отказы оформления, низкие остатки.
3. **Infrastructure** — CPU/RAM контейнеров (cAdvisor, node-exporter), состояние MySQL (mysqld-exporter): соединения, QPS, InnoDB buffer pool.
4. **Logs** — поток логов из Loki с фильтрами по уровню и `traceId`.

### 10.3. Логирование

- Serilog, вывод в stdout в формате JSON (`Serilog.Formatting.Compact`).
- Обогащение: `traceId`, `userId`, `requestPath`, `statusCode`, `elapsedMs`, `environment`.
- Уровни: `Information` — бизнес-события, `Warning` — бизнес-отказы, `Error` — необработанные исключения со стеком.
- Сбор: Promtail читает логи docker-контейнеров и пишет в Loki; срок хранения в стенде — 7 суток.

## 13. Ограничения и допущения

1. Платёжный шлюз имитируется; реальные транзакции и 3-D Secure не выполняются.
2. Единая валюта — российский рубль, без мультивалютности и налоговых режимов.
3. Единый склад; мультискладской учёт и резервирование по складам не поддерживаются.
4. Доставка рассчитывается по фиксированным тарифам, без интеграции со службами доставки.
5. Стенд рассчитан на одну реплику API; для нескольких реплик используются общий кэш (Redis) и внешнее хранилище файлов (MinIO), уже присутствующие в составе.
